# Movelet 기획안

> 선교사와 공동체를 위한 **초대제 프라이빗 커뮤니티 앱**
> 문서 버전 v0.8 · 2026-08-18 · 작성 단계: MVP 정의

---

## 1. 문제 정의

선교사들은 지금 **네이버 밴드·카페·단톡방**으로 소식을 나눈다. 여기서 세 가지가 계속 걸린다.

1. **외부로 새어나갈 통로가 남아 있다.** 초대받은 사람만 들어오는 구조는 밴드·카페도 마찬가지다. 문제는 그 다음이다. 웹 브라우저로 열리고, 설정 하나에 따라 검색에 걸리고, 링크가 밖으로 전달된다. 사역지 사진 한 장, 지역명 한 줄이 선교사와 현지 사역자에게 위험이 되는데 **플랫폼이 앱 바깥에 노출면을 계속 열어둔다.**

2. **공동체마다 채널이 갈라지고, 선교사는 같은 소식을 몇 번씩 올린다.** 파송교회 밴드, 선교단체 단톡방, 기도모임 카페 — 각 공동체는 자기 방 소식만 보면 되는 게 맞다. 그런데 방마다 앱이 다르니 선교사는 같은 기도제목을 서너 번 복사해 붙여 넣고, 어디에 무엇을 올렸는지 스스로도 헷갈린다.

3. **귀국 시 숙소 문제가 알음알음으로만 해결된다.** 안식년·보고 방문으로 귀국하면 머물 곳이 없다. 집이 없거나 비용을 감당하기 어려운 경우가 많은데, 숙소를 저렴하게 또는 무료로 내어주려는 사람은 분명 존재한다. 다만 서로를 찾을 방법이 인맥밖에 없다.

**이 앱의 목적은 모금이 아니라 커뮤니티다.** 기도제목을 나누고 소식을 주고받는 공동체가 중심이고, 후원과 숙소는 그 공동체 안에서 자연스럽게 필요해지는 부가 기능이다. 후원 모금 플랫폼을 만드는 것이 아니다.

## 2. 우리가 만드는 것

**초대받은 커뮤니티의 멤버만 그 커뮤니티의 자료를 본다. 그리고 앱 바깥에는 아무것도 나가지 않는다.**

이 두 문장이 제품 전체의 설계 원칙이다. 밴드·카페처럼 초대로 사람을 들이되, 그 방의 기도제목·사진·간증은 **그 방 사람들에게만** 보인다. 다른 커뮤니티 멤버에게도 보이지 않고, 웹에도 없고, 검색엔진에도 잡히지 않는다.

여기서 "공개"라는 말이 두 층위로 쓰이므로 미리 못 박아 둔다.

| 층위 | 의미 | 방침 |
|---|---|---|
| **앱 바깥** | 웹·검색엔진·비로그인 | **항상 닫혀 있다.** 어떤 방이든 예외 없다 |
| **앱 안** | 어느 회원까지 볼 수 있는가 | 커뮤니티 단위로 갈린다 (아래) |

그래서 커뮤니티는 두 종류다.

- **프라이빗 커뮤니티** (기본) — 초대받은 멤버만 열람·작성. 파송교회, 선교단체, 기도모임, 가족. 우리만의 방이다.
- **열린 커뮤니티(광장)** — 앱에 가입한 회원이면 누구나 볼 수 있는 방. 모두에게 열고 싶은 기도제목, 널리 알리고 싶은 후원 요청, 전체 공지가 여기로 간다. **회원 전체에게 열릴 뿐, 앱 바깥으로 나가지 않는 것은 똑같다.**

선교사 한 사람은 보통 여러 커뮤니티에 속한다. 소식 하나를 쓰면서 올릴 방을 여러 개 고를 수 있게 하는 것이 1절 두 번째 문제에 대한 답이다.

## 3. 타깃 사용자

**대상 지역**: 필리핀·일본·동남아·국내 등 **SNS 사용이 가능한 지역**의 선교사.
보안 통제가 극심해 일반 SNS 자체를 쓸 수 없는 지역은 이번 범위가 아니다. 다만 그런 지역의 선교사가 안전한 곳에 나왔을 때 쓸 수 있도록, 가명·지역 비공개 옵션은 처음부터 넣는다.

| 페르소나 | 상황 | 앱에서 하는 일 |
|---|---|---|
| **선교사** (핵심) | 필리핀에서 사역 중, 후원교회 3곳·개인 후원자 20여 명 | 소속 커뮤니티에 기도제목·사진·간증 올리기(여러 방 동시 선택), 후원 계좌 안내, 귀국 시 숙소 요청 |
| **커뮤니티 운영자** | 방을 만든 사람. 선교사 본인일 수도, 파송교회 선교부 담당자·선교단체 간사일 수도 있다 | 커뮤니티 개설, 멤버 초대·관리, 공지, 부적절한 글 처리 |
| **멤버(후원자·중보자)** | 파송교회 성도, 매달 후원 중 | 소속 방 소식 읽고 "기도했어요" 남기기, 댓글, 후원 계좌 확인 |
| **호스트** | 국내 거주, 빈방이나 사택이 있음 | 숙소 등록, 기간 설정, 요청 수락/거절, 특정 선교사에게만 열어주기 |
| **관리자** | 서비스 운영자(초기엔 haerim) | 선교사 인증 심사, 광장 관리, 신고 처리, 강제 탈퇴 |

한 사람이 여러 역할을 겸한다. 선교사가 호스트일 수도 있고, 후원자가 호스트인 경우가 가장 흔할 것이다. **역할은 계정 종류가 아니라 프로필에 붙는 속성이고, 커뮤니티 안에서의 권한은 그 방의 멤버십에 붙는다.**

## 4. 범위

### MVP (v1.0)
- 회원가입·로그인, 프로필 (**소속 교회 필수 입력**)
- **커뮤니티**: 개설(회원 누구나), 초대 링크·코드, 멤버 관리, 나가기
- **열린 커뮤니티(광장)**: 전체 회원 대상 방
- 선교사 인증(관리자 승인) 및 인증 뱃지
- 피드: 기도제목 / 간증 / 나눔 / 사진 — **작성 시 올릴 커뮤니티 선택(복수 가능)**
- "기도했어요" 반응, 댓글
- 후원 정보: 계좌 안내 (앱 내 결제 없음)
- 숙소: 호스트 등록 → 게스트 요청 → 수락/거절
- 푸시 알림
- 신고·차단

### v1.0에서 빼는 것 (의도적으로)
- 앱 내 결제·정산 → 5.4절 참고
- 실시간 채팅 → 요청 메시지로 대체, 이후 검토
- 커뮤니티 안의 하위 게시판·말머리 → 방 하나에 단일 피드로 시작한다
- 커뮤니티 검색·둘러보기 → 프라이빗 방은 목록에 뜨면 안 되고, 광장은 하나뿐이라 찾을 것이 없다
- 웹 버전 → 프라이버시 원칙상 웹은 노출면만 늘린다. 앱 전용으로 간다
- 다국어 → 한국어만

## 5. 기능 명세

### 5.1 커뮤니티

이 제품의 뼈대다. 다른 모든 콘텐츠는 커뮤니티에 속한다.

**개설 — 회원 누구나**
- 가입한 회원이면 누구나 만들 수 있다. 선교부 간사·기도모임 리더처럼 선교사보다 실무자가 먼저 움직이는 경우가 흔하고, 인증을 개설의 조건으로 걸면 그 사람들이 시작할 수 없다
- 만든 방이 프라이빗인 이상 **밖으로 새어나갈 것이 없다.** 방을 아무나 만들어도 그 안을 볼 수 있는 사람은 초대받은 멤버뿐이므로, 개설을 조여서 얻을 안전 이득이 크지 않다. 통제가 필요한 지점은 개설이 아니라 **광장**이고, 거기만 인증으로 막는다
- 입력: 이름, 소개, 커버 이미지, 성격(파송교회 / 선교단체 / 기도모임 / 기타)
- 만든 사람이 `운영자`가 되고, 다른 멤버에게 운영 권한을 넘기거나 나눠 줄 수 있다

**초대 — 유일한 입구**
- 초대 링크 또는 6자리 코드. 링크에는 **만료 시각과 사용 횟수 제한**을 건다
- 멤버 누구나 초대할 수 있는지, 운영자만 할 수 있는지는 방마다 설정한다 (기본값: 운영자만)
- 링크를 받아도 앱 설치·가입·로그인을 거쳐야 들어온다. 링크만으로 내용이 보이는 일은 없다
- 링크가 밖으로 샜을 때를 대비해 운영자는 **초대 링크를 언제든 무효화**할 수 있고, 들어온 멤버 목록을 항상 볼 수 있다

**멤버**
- 역할: `운영자` / `멤버`
- 운영자는 멤버 내보내기, 글 삭제, 공지 고정 가능
- 멤버는 언제든 나갈 수 있고, 나가면 그 방 자료가 즉시 안 보인다

**열린 커뮤니티(광장)**
- 서비스가 기본 제공하는 방. 개설·초대 없이 모든 회원이 처음부터 들어와 있다
- 모두에게 열고 싶은 기도제목, 널리 알리고 싶은 후원 요청, 운영 공지가 여기 올라간다
- **글쓰기는 인증된 선교사와 운영자만.** 모든 회원이 읽는 자리이므로 사칭·홍보·모금 사기의 표적이 되기 쉽다. 읽기는 전 회원, 쓰기는 인증자로 나눈다
- 광장 글에도 댓글·기도 반응은 전 회원이 남길 수 있다

### 5.2 계정 · 온보딩

**가입은 열려 있고, 열람은 방에 속해야 열린다.**

- 이메일 또는 카카오/애플 로그인
- 가입 직후 보이는 것: 자기 프로필, 앱 안내, **광장**
- 프라이빗 커뮤니티는 초대를 받아야만 존재조차 보이지 않는다
- 비로그인 상태에서 접근 가능한 서버 데이터는 없다

**소속 교회는 전원 필수 입력이다.**

프로필 설정 단계에서 건너뛸 수 없게 한다. 익명으로는 들어올 수 없는 앱이라는 뜻이고, 초대한 사람이 상대가 누구인지 확인할 수 있는 최소한의 근거가 된다.

| 대상 | 필수 입력 |
|---|---|
| 모든 회원 | **출석 교회** (교단·지역 포함 권장) |
| 선교사 — 파송 | 출석 교회 + **파송 교회** + 파송단체(선택) |
| 선교사 — 자비량·독립 | 출석 교회 + 사역 형태 명시 (파송 교회 없음을 선택) |

- 파송 교회와 출석 교회가 같으면 체크 한 번으로 끝낸다
- 입력은 자유 텍스트로 받되, 이미 등록된 교회명을 자동완성으로 제안해 표기 흔들림("○○교회" / "○○ 교회")을 줄인다. 교회 마스터 DB를 별도로 구축하는 것은 MVP 범위 밖이다
- **검증은 하지 않는다.** 거짓으로 적을 수 있다는 점은 인정한다. 다만 적어야 한다는 사실 자체가 진입 마찰이 되고, 방 운영자가 초대 전에 확인할 근거가 된다. 선교사 인증 심사에서는 이 값을 관리자가 실제로 대조한다

가입이 열려 있다는 건 신원이 확인되지 않은 사람도 들어온다는 뜻이다. 여기에 대한 장치를 네 겹으로 둔다.

1. **프라이빗 방은 초대가 문지기다.** 서비스가 신원을 보증하지 않아도, 그 방 운영자가 아는 사람만 들인다. 이것이 가장 강한 장치다
2. **소속 교회 필수 기재**: 위 표대로. 익명 가입을 막는다
3. **인증 뱃지**: 선교사는 파송교회·파송단체·추천인 확인 후 관리자가 인증을 부여한다. **인증은 광장 글쓰기, 후원 계좌 등록, 숙소 요청의 조건**이다. 즉 전 회원에게 열리거나 남의 집 주소가 걸린 행동에만 인증을 요구한다. 커뮤니티 개설과 프라이빗 방 안 글쓰기는 초대가 이미 검증 역할을 하므로 인증을 요구하지 않는다
4. **신고·차단·강제 탈퇴**: 사용자가 신고하면 방 운영자와 서비스 관리자에게 알림

**인증이 여는 것 정리**

| 행동 | 필요 조건 |
|---|---|
| 프라이빗 방 읽기·글쓰기·댓글 | 그 방의 멤버 |
| 광장 읽기·댓글·기도 반응 | 회원 누구나 |
| **광장 글쓰기** | 인증 선교사 · 운영자 |
| **커뮤니티 개설** | 회원 누구나 |
| **후원 계좌 등록** | 인증 선교사 |
| 숙소 등록(호스트) | 회원 누구나 |
| **숙소 요청(게스트)** | 인증 선교사 — 호스트의 집 주소가 걸린 일이므로 (5.5절) |

> 후속 검토: 가입 자체를 초대 코드제로 조일 수 있게, 정책을 코드가 아니라 설정값으로 둔다.

### 5.3 피드

게시글 타입 네 가지. 작성 화면은 하나이고 타입만 고른다.

| 타입 | 성격 | 특징 |
|---|---|---|
| **기도제목** | 가장 자주 쓰임 | "기도했어요" 반응, 응답받은 제목은 '응답' 표시로 전환 |
| **간증** | 긴 글 | 응답된 기도와 연결 가능 |
| **나눔** | 일상·소식 | 짧은 글 + 사진 |
| **사진** | 사역 현장 | 여러 장, 캡션 |

**어디에 올릴지를 글마다 고른다.** 공개 범위 설정이 아니라 **대상 커뮤니티 선택**이다.

- 내가 속한 커뮤니티 목록에서 **복수 선택**. 후원교회 세 곳에 같은 기도제목을 올릴 때 한 번만 쓰면 된다
- 광장을 선택하면 전 회원에게 열린다 (인증된 선교사만 가능)
- 기본값은 **직전에 올린 방**으로 두되, 광장은 기본 선택에 절대 포함하지 않는다. 실수로 전체에 열리는 일이 없어야 한다
- 홈 피드는 내가 속한 모든 방의 글을 시간순으로 합쳐 보여주고, 각 글에 어느 방 글인지 배지를 단다. 방별로 걸러 보기도 가능

여러 방에 올린 글의 **댓글과 반응은 방마다 따로 쌓인다.** 파송교회 성도들이 남긴 댓글이 다른 교회 방에 보이면 안 된다.

### 5.4 후원 — 계좌 안내 방식

다시 강조하면 **후원은 이 앱의 목적이 아니라 커뮤니티 안의 부가 기능**이다. 모금액을 키우는 장치(랭킹, 목표 게이지, 독촉 알림)는 넣지 않는다.

**v1.0은 앱이 돈을 만지지 않는다.** 선교사가 후원 계좌를 등록하고, 후원자는 그 정보를 보고 직접 송금한다.

- 선교사 프로필에 계좌 등록 (은행·예금주·계좌번호, 후원 QR, 안내 문구) — **인증된 선교사만**
- 계좌 노출 범위: **같은 커뮤니티 멤버에게만**이 기본. 광장에 후원 요청 글을 올린 경우에 한해 전 회원에게 열린다
- 계좌번호는 **암호화 저장**하고, 복사 버튼으로 전달
- 후원자가 "후원했어요"를 남기면 선교사에게 알림 (금액은 받지 않는다 — 자진 기록일 뿐)

**왜 앱 내 결제를 안 하는가**
사업자등록·PG 심사·기부금품법 검토가 필요하고, 애플·구글 인앱결제 정책과 수수료 문제가 걸린다. 무엇보다 이 셋을 정리하는 동안 정작 핵심인 커뮤니티가 못 나온다. **v2 로드맵에 남기되, MVP는 중개만 한다.**

### 5.5 숙소

이 앱의 차별점이자, 가장 조심해서 만들어야 할 기능이다.

숙소는 **커뮤니티 안이 아니라 앱 전역 기능**으로 둔다. 매칭은 후보가 많아야 성립하는데, 한 방 안에서만 찾으면 사실상 지금의 인맥과 다를 게 없기 때문이다. 대신 공개 범위를 호스트가 좁힐 수 있게 한다.

**호스트 흐름**
1. 숙소 등록: 사진, 지역(시·구 단위), 수용 인원, 가능 기간, 비용(무료 / 실비 / 금액), 하우스 룰
2. 공개 범위 선택: `전체 회원` / `특정 커뮤니티 멤버에게만` / **`특정 선교사에게만`** (개인 집을 한 분을 위해 잠시 내어주는 경우)
3. 요청이 오면 수락·거절
4. 언제든 내리기 (등록·삭제는 호스트 권한)

**게스트(선교사) 흐름**
1. 지역·기간·인원으로 검색
2. 요청 보내기 (귀국 목적, 인원, 희망 기간, 메시지) — **인증된 선교사만 요청할 수 있다.** 호스트의 집 주소와 연락처가 열리는 일이라 여기서는 초대가 아니라 서비스 인증이 문지기가 되어야 한다
3. 수락되면 **그때 상세 주소와 연락처가 열린다**

호스트에게는 요청자의 **인증 뱃지·소속 교회·파송 교회**가 함께 보인다. 낯선 사람에게 집을 내어주는 결정이므로, 판단에 필요한 최소 정보는 요청 화면에서 제공한다.

**핵심 안전장치: 주소는 수락 전까지 마스킹한다.** 목록·상세에서는 "서울 은평구"까지만 보인다. 상세 주소·연락처는 호스트가 요청을 수락한 뒤에만 양쪽에 공개된다. 호스트의 집 주소가 회원 전체에게 열려 있어서는 안 된다.

### 5.6 알림

푸시로 보낼 것: 내 글에 달린 기도/댓글, 커뮤니티 초대·공지, 숙소 요청 도착, 요청 수락·거절, 후원 알림, 관리자 공지.
알림 내용에는 민감 정보를 넣지 않는다 (잠금화면에 사역지나 주소, 커뮤니티 이름이 뜨면 안 된다).

### 5.7 신고 · 차단

모든 글·프로필에 신고. 신고는 **먼저 그 방 운영자에게** 가고, 광장 글이거나 운영자가 처리하지 않으면 서비스 관리자에게 올라간다. 차단하면 서로의 콘텐츠가 안 보인다.

## 6. 프라이버시 설계

제품의 약속이므로 별도 절로 둔다.

| 항목 | 방침 |
|---|---|
| **기본 거부** | DB는 Row Level Security로 전 테이블 기본 차단. **모든 조회 권한의 뿌리는 "내가 그 커뮤니티의 멤버인가"** 하나로 통일한다 |
| **커뮤니티 격리** | 다른 방의 글·댓글·멤버 목록은 존재 자체가 조회되지 않는다. 방 이름조차 비멤버에게 노출하지 않는다 |
| **비로그인 접근** | 없음. 공개 API 엔드포인트를 두지 않는다 |
| **초대 링크** | 만료·사용 횟수 제한, 운영자가 즉시 무효화 가능. 링크 소지만으로 내용이 열리지 않는다 |
| **이미지** | 비공개 스토리지 + 단기 만료 서명 URL. URL이 유출돼도 곧 만료된다 |
| **웹·검색 노출** | 웹 버전을 만들지 않는다. 크롤링 대상이 존재하지 않는다. **광장 글도 예외가 아니다** |
| **위치·지역** | 사역 국가 표기는 선택. 가명 사용 가능. 위험지역은 "동아시아" 수준으로만 |
| **소속·파송 교회** | 입력은 전원 필수지만 **노출은 같은 커뮤니티 멤버와 숙소 요청 상대에게만**. 파송 교회가 곧 사역지 단서가 되는 경우가 있어, 선교사에게는 `파송 교회 비공개`(관리자·심사에만 보임) 옵션을 준다 |
| **숙소 주소** | 요청 수락 전까지 시·구 단위 마스킹 |
| **후원 계좌** | 암호화 저장, 같은 커뮤니티 멤버에게만 노출 (광장 후원 글은 예외) |
| **탈퇴** | 탈퇴 시 게시물·이미지 완전 삭제 (soft delete 후 30일 내 물리 삭제) |
| **스크린샷** | 기술적으로 막을 수 없다. 대신 가입 시 "캡처·외부 공유 금지" 서약을 받고, 위반 신고 시 강제 탈퇴 |

**솔직히 말해 둘 것**: 초대받은 사람이 캡처해서 밖으로 내보내는 것은 어떤 앱도 막지 못한다. 이 앱이 보장하는 것은 **"앱 바깥에 노출면을 만들지 않는다"와 "방 밖 사람에게는 아무것도 보이지 않는다"** 두 가지다. 정말 위험한 정보는 이 앱에도 올리지 않도록 온보딩에서 명확히 안내한다.

## 7. 데이터 모델 (초안)

```
profiles           id, display_name, avatar, bio,
                   home_church NOT NULL,              -- 출석 교회, 전원 필수
                   is_missionary, verified_at, verified_by, created_at
missionary_info    profile_id, missionary_type(sent|self_supported|other),
                   sending_church,        -- type='sent' 이면 필수
                   agency, field_country, field_label, ministry_desc,
                   is_location_hidden, is_church_hidden
churches           id, name, region, denomination   -- 자동완성용 누적 사전
support_accounts   missionary_id, bank, holder, account_no_enc, qr_url, note

communities        id, name, kind(church|agency|prayer|etc), description,
                   cover_path, type(private|open), invite_policy(owner|member),
                   created_by, created_at
community_members  community_id, user_id, role(owner|member),
                   invited_by, joined_at
community_invites  id, community_id, code, created_by,
                   expires_at, max_uses, used_count, revoked_at

posts              id, author_id, type(prayer|testimony|share|photo),
                   body, is_answered, is_self_only, created_at
post_targets       post_id, community_id            -- 복수 방 동시 게시
post_media         post_id, storage_path, order
comments           id, post_id, community_id, author_id, body, created_at
reactions          post_id, community_id, user_id, kind(prayed|amen)
support_logs       missionary_id, supporter_id, created_at   -- 금액 저장 안 함

stays              id, host_id, title, region_label,
                   capacity, available_from, available_to,
                   cost_type(free|actual_cost|paid), cost_amount,
                   house_rules, visibility(members|community|targeted), status
stay_addresses     stay_id, address_line, address_detail, contact
                                                   -- 수락된 게스트와 호스트만 열람
stay_media         stay_id, storage_path
stay_audience      stay_id, community_id, missionary_id   -- 지정 공개 대상
stay_requests      id, stay_id, guest_id, message, date_from, date_to,
                   headcount, status(pending|accepted|declined|cancelled)

reports            id, reporter_id, community_id, target_type, target_id,
                   reason, status
blocks             blocker_id, blocked_id
notifications      id, user_id, type, payload, read_at
```

**설계 메모**
- `posts`에 `community_id`를 직접 두지 않고 `post_targets`로 뺀 이유는 한 글이 여러 방에 걸리기 때문이다. 열람 권한은 "이 글의 target 중 내가 멤버인 방이 하나라도 있는가"로 판정한다
- `comments`·`reactions`에 `community_id`가 붙는 이유는 **방마다 대화가 따로 쌓여야** 하기 때문이다. 이게 없으면 A교회 댓글이 B교회에 보인다
- `home_church`는 DB 레벨 `NOT NULL`로 강제한다. 앱 화면에서만 필수로 두면 우회 경로가 남는다
- `churches`는 사용자가 입력한 교회명을 누적해 자동완성에 쓰는 보조 테이블이다. 정규화된 마스터 데이터가 아니며, `profiles.home_church`는 이 테이블을 참조하지 않고 문자열로 저장한다 (교회명을 못 찾아 가입이 막히는 일이 없어야 한다)
- 광장은 `communities`의 한 행(`type='open'`)으로 둔다. 특별 취급을 코드에 흩뿌리지 않고 멤버십 판정 한 곳에서만 분기한다
- 숙소 상세 주소는 `stays`의 컬럼이 아니라 **`stay_addresses` 별도 표**다. RLS는 행 단위라 컬럼 하나만 가릴 수 없다. 주소를 다른 행에 두어야 "수락 전까지 마스킹"이 DB에서 강제된다 (M0 구현 중 확정)
- 방 개설과 초대 참여는 정책이 아니라 **RPC**(`create_community`·`join_community_by_code`·`preview_invite`)로 처리한다. 둘 다 "아직 멤버가 아닌 순간"을 다뤄야 해서 멤버십 기반 정책으로는 풀리지 않는다. 판정의 뿌리를 멤버십 하나로 유지하려고 예외를 정책이 아닌 함수 쪽에 몰았다 (M0 구현 중 확정)

## 8. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 앱 | **React Native + Expo** (TypeScript) | iOS/Android 한 코드베이스. Expo로 푸시·이미지·카메라가 바로 붙는다 |
| 라우팅 | Expo Router | 파일 기반, 딥링크 대응 (초대 링크에 필요) |
| 백엔드 | **Supabase** (Postgres + Auth + Storage) | **RLS가 이 제품의 프라이버시 요구와 정확히 맞는다.** 커뮤니티 멤버십 기반 정책을 DB에 박아두면 앱 실수로도 다른 방 데이터가 새지 않는다 |
| 인증 | Supabase Auth (이메일 + 카카오 + Apple) | 애플 로그인은 iOS 심사 필수 |
| 스토리지 | Supabase Storage 비공개 버킷 + 서명 URL | |
| 푸시 | Expo Notifications | |
| 상태·데이터 | TanStack Query + Zustand | |
| 배포 | EAS Build / EAS Update | OTA 업데이트로 심사 없이 수정 가능 |
| 에러 추적 | Sentry | |

**대안 검토**: 백엔드를 직접 만들면(NestJS 등) 자유도는 높지만 인증·스토리지·권한을 전부 짜야 한다. 1인 개발에서 MVP까지 가는 속도가 압도적으로 다르므로 Supabase로 간다. 나중에 Postgres째로 들고 나올 수 있어 락인도 크지 않다.

## 9. 화면 구조

```
[온보딩]  스플래시 → 로그인/가입 → 프로필 설정(이름·사진)
          → **소속 교회 입력(필수)** → 선교사 여부 → (선교사면) 파송 형태·파송 교회
          → 서약 동의
          (초대 링크로 진입한 경우 → 가입 직후 해당 커뮤니티 참여 확인)

[탭 1] 홈       내 모든 방의 글 합친 피드(방 배지) · 방별 필터 · 글쓰기
[탭 2] 커뮤니티 내 방 목록 → 방 피드 / 멤버 / 초대 / 설정  ·  광장  ·  방 만들기
[탭 3] 숙소     검색 → 상세 → 요청  |  내 숙소 관리(호스트)
[탭 4] 알림
[탭 5] 내 정보  프로필 편집 · 후원 계좌 관리 · 내 요청 · 설정 · 차단 목록
[관리자] 선교사 인증 심사 · 광장 관리 · 신고 처리   (별도 화면, 권한자만)
```

**글쓰기 화면**은 타입 선택 → 본문·사진 → **올릴 커뮤니티 선택(복수)** 순서다. 마지막 단계에서 선택된 방 이름을 크게 보여줘, 어디로 나가는 글인지 착각할 수 없게 한다.

## 11. 성공 지표

MVP 단계에서는 숫자보다 **"밴드를 대체했는가"**가 기준이다.

- 베타 커뮤니티에서 **주 1회 이상 글이 올라오는 방의 비율** (목표 60%)
- 선교사 한 명당 **소속 커뮤니티 수** — 2개 이상이면 다중 게시가 실제로 쓰이고 있다는 뜻
- 기도제목당 "기도했어요" 수 (목표 평균 5 이상)
- **숙소 매칭 성사 건수** — 이 앱만 할 수 있는 일. 베타 기간 중 1건이라도 성사되면 유의미
- 멤버 주간 재방문율

후원 금액이나 후원자 수는 지표로 삼지 않는다. 목적이 아니기 때문이다.

## 12. 리스크 · 미결 사항

| 리스크 | 대응 |
|---|---|
| 초대 링크 외부 유출 | 만료·횟수 제한, 즉시 무효화, 멤버 목록 상시 확인. 링크만으로는 열람 불가(가입·로그인 필수) |
| 커뮤니티 간 데이터 누출 | 권한 판정을 멤버십 한 곳으로 통일하고 RLS로 강제. 방 간 격리는 **테스트를 따로 작성해 회귀로 막는다** |
| 광장이 홍보·모금 게시판이 됨 | 광장 글쓰기는 인증 선교사·운영자로 제한, 신고 즉시 관리자에게 |
| **인증이 병목이 됨** | 광장 글쓰기·후원 계좌·숙소 요청이 인증에 걸린다. 커뮤니티 개설을 인증에서 뺀 덕에 **인증이 늦어도 방을 만들고 초대해 쓰는 것은 막히지 않는다.** 그래도 베타 기간에는 관리자 심사 SLA를 24시간 내로 잡고, 심사 대기 화면에서 상태를 보여준다 |
| **방 난립·스팸 방 개설** | 개설을 열어 둔 대가. 프라이빗 방은 밖에서 안 보이므로 피해 범위가 방 안으로 한정되지만, 계정당 개설 수 상한과 신고 기반 관리자 삭제를 둔다. 활동 없는 빈 방은 일정 기간 후 정리 안내 |
| 교회명 표기 흔들림 | 자동완성으로 줄이되 강제하지 않는다. 동명 교회가 많아 정규화는 MVP 범위 밖 |
| 콘텐츠 유출(스크린샷) | 기술적 차단 불가. 서약 + 제재 + "정말 위험한 정보는 올리지 말 것" 안내 |
| 방이 너무 잘게 쪼개져 아무도 안 씀 | 초기엔 파송단체·교회 단위로 큰 방부터 만든다. 개설은 열되 권장 단위를 온보딩에서 안내 |
| 숙소 분쟁 (파손·노쇼) | v1은 앱이 책임지지 않음을 명시. 후기 기능은 v2 |
| 후원 계좌 정보 유출 | 암호화 + 커뮤니티 멤버 한정 노출 + 접근 로그 |

**확정**
- **앱 이름 — Movelet** (`move` + `letter`). 선교사가 보내는 기도편지가 원형이고, 움직임이 더해져 "움직이는 편지 한 통"이 된다. 리포·번들 ID·딥링크 스킴 모두 `movelet` 로 통일.
  - 상표·스토어는 예비 조회만 마친 상태(동명 앱 없음). 출원 전 KIPRIS·USPTO 정식 조회 필요
  - `movelet` 은 가속도계 활동인식 학술 용어, SAP Movilizer 의 XML 객체명으로도 쓰인다. 상표 충돌은 아니지만 영문 SEO 에서 경쟁이 있다

**결정 대기**
- **광장의 이름** — 사용자에게 보일 명칭 ("광장", "열린 나눔", "전체" 등)
- 광장을 하나만 둘지, 주제별로 몇 개 둘지 (기도 / 후원 / 공지)
- 개인정보처리방침·이용약관 문안 (스토어 심사 필수)
- 운영 주체 — 개인 명의인지 단체 명의인지에 따라 약관과 v2 결제가 달라진다
